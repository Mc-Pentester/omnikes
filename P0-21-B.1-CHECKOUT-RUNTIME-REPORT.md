## 5. INSPECTION DE LA ROUTE

### Ordre d'exécution identifié :

1. **Ligne 21 :** `requireCurrentOrganizationId(request)` - Authentification + organisation
2. **Ligne 22 :** `getAuthenticatedUser(request)` - Récupération utilisateur
3. **Ligne 31-32 :** `requirePermission(request, ...)` - Vérification permissions
4. **Ligne 35-41 :** Validation header `Idempotency-Key`
5. **Ligne 44-45 :** Parsing données paiement
6. **Ligne 48-55 :** Lecture idempotency existante (lecture seule)
7. **Ligne 98-101 :** `prisma.sale.findUnique` pour récupérer `storeId` et `organizationId`
8. **Ligne 111-116 :** Vérification organisation (tenant boundary)
9. **Ligne 119-128 :** `requireStoreAccess(request, storeId)` - **Contrôle RBAC store scope**
10. **Ligne 131 :** `prisma.$transaction` - Début transaction atomique

### Point critique :

Le contrôle `requireStoreAccess` est exécuté **avant** la transaction (ligne 119-128 vs ligne 131).

La lecture idempotency (ligne 48-55) est une lecture seule par `organizationId + key`, ce qui ne constitue pas une mutation cross-store.

## 8. IDEMPOTENCY

### Ordre idempotency / store access :

```
1. findUnique checkoutIdempotency (lecture seule)
2. requireStoreAccess (contrôle sécurité)
3. $transaction (création idempotency + mutations)
```

### Analyse :

- La lecture idempotency (étape 1) est une lecture seule par `organizationId + key`
- Cette lecture ne révèle pas d'information cross-store sensible
- La création idempotency (étape 3) se produit uniquement à l'intérieur de la transaction
- Puisque `requireStoreAccess` rejette avant la transaction, aucune création idempotency n'a lieu

**Conclusion :** Aucun problème d'ordre idempotency / store access.

Les tests P0-21-B.1 utilisent des mocks pour isoler le comportement du handler API. Bien que cela ne constitue pas une preuve runtime contre une base de données réelle, les tests :

1. Exécutent le véritable handler API (`POSTCheckout`)

Pour une preuve runtime complète contre une base de données réelle, il serait nécessaire de :
- Exécuter les tests contre une instance PostgreSQL de test
- Créer des fixtures de vente réelles dans la base
- Exécuter les requêtes HTTP réelles

Cependant, les tests actuels suffisent à démontrer que l'architecture de sécurité est correcte et qu'aucun bypass n'est possible au niveau du code.
