## 19. Cause racine

**G. AUTRE - PROBLÈME DE SESSION/PERMISSION**

**Analyse:**

L'investigation forensic démontre que:
1. L'intégrité des données est correcte (Sale.organizationId === Store.organizationId)
2. Le tenant boundary est respecté
3. Les ventes récentes n'ont aucune incohérence
4. Le saleId utilisé pour le paiement est correct
5. La source d'organizationId est identique pour création et paiement
6. Aucun risque de stale ID

**Conclusion:**

Le 404 sur `POST /api/sales/{saleId}/payments` n'est PAS causé par:
- Incohérence de données (Sale.organizationId ≠ Store.organizationId)
- Divergence de contexte tenant entre création et paiement
- Stale saleId
- Mismatch frontend/DB

**Cause probable:**

Le 404 provient très probablement d'un problème de **session ou de permission** au moment de l'appel payment:
- L'utilisateur a peut-être perdu sa session entre création et paiement
- L'utilisateur n'a peut-être pas la permission `payment.create`
- L'organizationId de la session a peut-être changé entre création et paiement (multi-organization user)
- Le token de session a peut-être expiré

**Recommandation:**

Ajouter des logs détaillés dans la route payments pour capturer:
- L'organizationId extrait de la session
- L'état de la session (valid/invalid)
- Les permissions de l'utilisateur
- Le résultat exact de `saleService.getById(id, organizationId)`
